Cursor · Git · GitHub · Vercel

Van idee naar productie, zonder het overzicht te verliezen.

Je werkt niet in één “versie”, maar in meerdere kopieën van dezelfde code. Zodra je weet welke kopie waarvoor dient, wordt de rest voorspelbaar.

1
De hoofdregel: één taak, één branch, één pull request. En pas na samenvoegen is het onderdeel van de gedeelde nieuwste versie.

Waarom je nu steeds het overzicht verliest

Dat is geen persoonlijk probleem. De huidige werkwijze maakt verwarring bijna onvermijdelijk.

1

Elke Cursor-sessie heeft een eigen kopie

Een Cloud Agent ziet wijzigingen uit een andere sessie pas nadat die zijn gecommit, gepusht en opgehaald.

2

Een commit reist niet vanzelf

Een commit zit op één branch. Andere branches blijven op hun eigen versie staan totdat je merge’t of rebase’t.

3

Een groene preview is niet altijd de app

Vercel controleert web- en backendonderdelen. Het bewijst niet dat de Swift/macOS-interface is gebouwd.

4

main en v2-main lopen naast elkaar

Daardoor kan “de nieuwste versie” twee betekenissen hebben: de algemene hoofdbranch of de v2-appbranch.

5

Parallel werk raakt dezelfde bestanden

Twee agents die tegelijk EditorView.swift aanpassen, maken allebei geldige maar onderling botsende versies.

6

Screenshots hebben geen herkomstlabel

Zonder branch, commit en buildnummer weet je niet of een screenshot lokaal, uit Figma of uit een gedeelde build komt.

De klassieke valkuil: “Cursor heeft het gefixt” betekent alleen dat één werkkopie is aangepast. Het betekent nog niet dat GitHub, je Mac, een andere Cloud Agent of productie die fix al bevat.

De zes regels die 90% van de chaos voorkomen

Wijs één hoofdbranch aan.

Voor de huidige v2-interface is dat v2-main. Start elke nieuwe v2-taak vanaf de nieuwste remote versie daarvan.

Eén taak = één branch = één PR.

Stop geen losstaande feature, bugfix en refactor in dezelfde branch.

Controleer bestaand werk vóór je een agent start.

Laat Cursor eerst open PR’s, actieve Cloud-sessies en overlappende bestanden inventariseren.

Werk niet parallel in dezelfde kernbestanden.

Als twee taken allebei EditorView.swift raken: na elkaar uitvoeren of één integratie-eigenaar aanwijzen.

Label ieder bewijs met branch + commit.

Bij elke screenshot of build: vermeld branch, korte commit-SHA en omgeving. Bijvoorbeeld v2-main @ 7fcc346 · lokale macOS-build.

Een taak is pas klaar na merge én verificatie.

“PR gemaakt” is niet hetzelfde als “staat in de nieuwste versie”.

Beste werkwijze voor een bugfix

Het proces

  1. Leg huidig en gewenst gedrag vast.
  2. Noteer hoe je de fout reproduceert.
  3. Controleer of er al een branch of PR voor bestaat.
  4. Start vanaf de nieuwste hoofdbranch.
  5. Maak de kleinst mogelijke fix.
  6. Test de relevante route en regressies.
  7. Commit, push en open één PR.
  8. Merge; haal daarna lokaal de hoofdbranch opnieuw op.

Zo gebruik je meerdere Cursor-sessies veilig

Veilig parallel

Gescheiden gebieden

Agent A werkt aan backend-auth. Agent B werkt aan documentatie. Ze raken geen gedeelde kernbestanden.

Voorzichtig

Zelfde feature, andere lagen

Spreek interfaces vooraf af. Laat één integratie-agent beide branches combineren en testen.

Niet parallel

Zelfde view of model

Twee agents die tegelijk EditorView, BoardView of dezelfde migratie wijzigen. Voer deze taken na elkaar uit.

Praktische limiet: maximaal één actieve implementatiesessie per featuregebied, plus eventueel één aparte onderzoek- of reviewsessie die geen bestanden wijzigt. 
Voordat je begint:
1. Inventariseer alle actieve Cursor Cloud-sessies voor deze repository.
2. Inventariseer alle open PR's met doelbranch v2-main.
3. Vergelijk de gewijzigde bestanden met deze taak.
4. Als een bestaande branch hetzelfde werk bevat: ga daarop verder of maak een integratieplan.
5. Start pas een nieuwe branch als er geen overlappende eigenaar is.

Prompttechnieken die veel verschil maken

1. Geef context die een computer kan controleren

Niet: “werk aan de nieuwste versie”.

Wel: “fetch origin/v2-main, meld de startcommit en controleer open PR’s”.

2. Scheid huidig en gewenst gedrag

Gebruik altijd AR (actual result) en ER (expected result). Dat voorkomt interpretatieverschillen.

3. Noem wat niet mag veranderen

Een scherpe “non-goal” voorkomt dat een kleine fix onbedoeld een hele UI-flow herschrijft.

4. Vraag om bewijs, niet om vertrouwen

Vraag om tests, branch, commit, PR, screenshot-herkomst en bekende beperkingen.

5. Laat onzekerheid expliciet melden

“Als de screenshot niet bij de broncode past, stop en rapporteer het verschil vóór implementatie.”

6. Geef één eindtoestand

Bijvoorbeeld: “klaar wanneer de PR mergebaar is, checks groen zijn en de macOS-flow handmatig is bevestigd”.

Controleprompt na afloop:

Bewijs dat deze wijziging echt in de bedoelde versie zit:
- Wat was de exacte startcommit?
- Wat is de featurebranch?
- Welke commits zijn toegevoegd?
- Is de branch gebaseerd op de nieuwste origin/v2-main?
- Welke andere branches/PR's overlappen?
- Welke tests zijn uitgevoerd?
- Test Vercel hier alleen web/backend, of ook de macOS-app?
- Uit welke branch + commit kwam de screenshot?
- Wat moet nog gemerged of lokaal opgehaald worden?

Concreet advies voor deze Aaavatar-repository

Tijdens de v2-overgang

  • Gebruik v2-main als enige integratiebasis voor werk in Avatar2/.
  • Laat elke v2-feature-PR uitsluitend naar v2-main wijzen.
  • Start afhankelijke taken pas nadat de vorige PR is gemerged.
  • Wijs bij parallel werk één integratiebranch en één eigenaar aan.
  • Behandel Vercel-checks niet als bewijs voor de macOS-UI.

Na de v2-release

  • Kies één permanente hoofdbranch, bij voorkeur main.
  • Merge de volledige v2-lijn gecontroleerd naar die branch.
  • Archiveer of hernoem de oude appbron zodat “main” en “v2” niet blijven concurreren.
  • Documenteer apart: web deploy, backend deploy en macOS release.
  • Gebruik release-tags voor exacte productieversies.
Belangrijk: zet niet zomaar v2-main over main. Backend-, admin-, release- en appwijzigingen moeten eerst als één integratieverschil worden beoordeeld.

De korte checklist

  • Ik weet welke hoofdbranch geldt.
  • Ik heb eerst remote updates opgehaald.
  • Ik heb open PR’s en sessies gecontroleerd.
  • Mijn taak heeft één branch en één PR.
  • Mijn branch raakt geen parallel beheerde kernbestanden.
  • Elke screenshot noemt branch en commit.
  • Ik weet wat Vercel wel en niet test.
  • Ik heb relevant gedrag getest.
  • De PR is mergebaar en beoordeeld.
  • Na merge heb ik de hoofdbranch opnieuw opgehaald.
✓
Klaar betekent: gemerged, opgehaald en geverifieerd. Niet alleen: “de agent heeft een commit gemaakt”.
